# 分享提纲：「研发+AI」全栈交付工作范式的探索与实践

基于 GenlotVPN-Cloud 项目的真实经验。

**核心主题：** 后端工程师如何借助 AI，通过结构化的人机协作范式，完成原本需要跨团队的全栈交付（云端服务 + 管理端 Web + 跨平台桌面客户端）。

**讲述人：** 后端工程师（Java/C++ 熟练，Vue/Qt 零基础）  
**项目：** GenlotVPN 统一 VPN 管理平台  
**时长：** 40 分钟（35 分钟讲述 + 5 分钟问答）

## 三、人机协作模式（10 分钟，4 页）

### 页 5：四个核心原则
**讲稿：**
这是整个工作范式的基础，不是编码技巧，而是协作原则：

1. **人定边界：** 安全级别、技术选型、架构约束由人确定，不是 AI 说了算
2. **AI 列方案：** AI 对比 2-3 个方案，列优缺点，但不直接开写
3. **人拍板：** 人基于约束做决策，结果落 ADR 文档（架构决策记录）
4. **门禁管控：** 未批 spec 不写码、S0 只人验、门禁脚本可重入

**关键点：** AI 不是编码工具，而是架构助手 + 实现加速器

### 页 6：三次关键共创决策
**实例说明：**

| 决策点 | AI 倾向 | 人决策 | 依据 |
|--------|---------|--------|------|
| 后台框架 | 自研/升 Boot 3 | 若依 3.6.8 | Java 8 约束，一人维护 |
| 客户端技术 | Electron | Qt 6 + QML | 安全面、原生、C++ 可迁移 |
| 传输协议 | 复用 HTTP | TLS + Protobuf | 抓包风险 |

**讲稿：**
- 每次都是先给约束（一人、Java 8、Win+Mac、过抓包）
- AI 列出方案和风险
- 人基于安全、维护成本、能力边界决策
- 决策落盘到 ADR 文档（现场可打开 ADR-001、ADR-002）

### 页 7：节首页 - 六阶段工作法
**讲稿：**
- 有了原则，还需要流程保证可重复
- 六阶段是让 AI 协作可管、可控、可复现的轨道

### 页 8：六阶段详解
**六个阶段：**
- **① 拆解、② 共创：** 人工主导，模块清单、spec 人批、未批不写码
- **③ 突破、④ 生成：** AI 执行，陌生域先 Demo、熟悉域按参照
- **⑤ 门禁、⑥ 回修：** 质量管控，gate→deploy→accept，回修≤2 轮

**讲稿：**
- 前两阶段是设计（人主导）
- 中间两阶段是实现（AI 加速）
- 最后两阶段是验证（脚本+人工）
- 客户端 S0（安全）只人验，不进自动 accept

## 四、质量管控（6 分钟，2 页）

### 页 9：质量门禁三道关
**讲稿：**
- **gate：** 构建、单测、静态检查、环境预检
- **deploy：** 三节点部署、服务健康、日志无异常
- **accept：** 业务验收脚本、API 断言、端到端流程
- 所有命令可重入、可自动化
- 输出记录到 `质量门禁.md`，时间戳可追溯

### 页 10：安全分级
**三级安全验收：**
- **S0 - 只人验：** TLS 配置、证书 Pin、密钥不进日志、抓包验密文
- **S1 - 人审逻辑：** 登录拦截、多线路同步、权限校验
- **S2 - 脚本断言：** 只读查询、策略页、反馈列表

**讲稿：**
- S0 永远只人验
- TLS 栈配好了 ≠ 每条新功能自动过 S0
- 这是对 AI 的约束，也是对自己的约束

## 五、架构与实现（8 分钟，3 页）

### 页 11：节首页
**讲稿：**
- 技术架构不是为了炫技，是为了满足「一人+AI 能维护」的约束

### 页 12：系统架构四层
**讲稿：**
1. **管理端：** Vue 2 + Element UI → Nginx → Gateway :8080
2. **云端服务：** Spring Cloud、Nacos、yianlian 模块（核心业务）
3. **桌面客户端：** Qt 6 + QML、直连 vpn-auth :9443、TLS 1.3
4. **本地隧道：** 易安联 Agent HTTP :30303（厂商不可改）

**关键点：**
- 管理端和桌面端是两张皮
- 管理端走 HTTP 网关（浏览器）
- 桌面端直连 9443 TLS（安全）

### 页 13：双服务层设计
**讲稿：**
- 易安联模块是核心难点
- 双服务层：
  - **本地层：** IVpnXxxService → MySQL
  - **远程层：** IYiAnLianXxxService → 远程平台 HTTP API
- **映射表：** `*YianlianMapping` 维护本地 ID ↔ 远程 ID
- **多线路：** 一条本地变更同步到多台设备（每个设备独立 ID 空间）

### 页 14：桌面端技术选型
**四个技术点：**
1. **Qt 6：** 跨平台原生、C++ 熟悉度可迁移
2. **QML：** 声明式 UI、学习曲线比 Qt Widgets 平缓
3. **TLS 1.3：** TCP :9443、证书 Pin、抓包密文
4. **Protobuf：** 契约在 proto/vpn、Java/C++ 共用

**讲稿：**
- 为什么不选 Electron？安全面大、非原生、一人难维护
- Qt 虽陌生，但 C++ 基础可迁移，QML 比 Widgets 好学
- TLS 是硬约束，不能妥协

## 七、边界与总结（3 分钟，1 页）

### 页 19：边界与不足
**四个边界：**
1. **客户端验收：** S0 只人验、不自动识别验证码、不用页面文案代替抓包
2. **投产范围：** 内部使用、未规模化投产、下载页内网 accept
3. **方法推广：** 本部门已用、换仓需调整、不是全公司自动化

**讲稿：**
- 主动讲边界，避免被问穿
- 不说无人审、不说已投产、不说客户端自动验收
- 这是一个工作范式的探索，不是完美的 AI 自动化

**核心价值总结：**
- 验证了「后端工程师 + AI → 全栈交付」的可行路径

## 八、问答预案（5 分钟）

### Q1：「不就是套了若依吗？AI 到底干了啥？」
**答：**
- 若依是共创后取的管理壳（AI 列过自研/升 Boot 3，人按 Java 8 约束选的若依）
- AI 的价值：
  1. 架构共创（列方案、对比风险）
  2. 陌生域突破（Vue/Qt 零基础 → 能交付）
  3. 三层联调加速（管理端、云端、桌面同步实现）
- 核心是 yianlian 模块（双服务层 + 多线路映射），不是套了个壳

### Q2：「AI 会不会把密钥写进仓库？」
**答：**
- 凭证只走本机 `pipeline/deploy/envs.yaml`（不入库）
- Hook 拦疑似密钥
- 对话和报告用 `***` 脱敏
- 这是 S0 验收内容，人工审查

### Q3：「为什么客户端不自动验收？」
**答：**
- S0（安全）不能用页面文案代替抓包
- TLS 证书 Pin、密文传输需要人工确认
- 自动验会倒逼关验证码或识图，和安全红线冲突
- PHASE2 清单是人工对照，不进 accept.py 退出码

### Q4：「下载页算不算又做了一个前端突破？」
**答：**
- 不是管理端、也不是 Qt
- 是 93 静态站（免登录、中英文）
- 把 16 日策略里的下载 URL 落到真包
- 陌生域突破仍看 ADR-001（Qt）+ PHASE2

### Q5：「这套方法能推广到其他项目吗？」
**答：**
- SOP 已在本部门推广
- 换仓需要适配（门禁脚本、技术栈）
- 不是全公司自动化，需要人定制
- 18 日验证过迁移到另一仓库（有搬迁说明文档）

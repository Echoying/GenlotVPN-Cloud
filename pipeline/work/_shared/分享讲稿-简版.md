## 二、架构演进（10分钟）

### 页3：节首页

**过渡：** 先讲清楚两个关键决策，才能理解后面的工作方法。

### 页4：从0构建的成本问题

**讲稿：**

最初的想法很直接：让AI从0生成一个Spring Boot微服务框架。

**遇到的问题：**
- **token消耗巨大** — 权限、菜单、网关、认证这些基础框架，AI生成代码量大、token成本高
- **不是核心价值** — 基础设施不是VPN业务的核心，多线路同步才是
- **调试周期长** — 生成的基础代码需要大量调试

**关键认知：**  
应该聚焦VPN业务逻辑（多线路同步、ID映射），不是重造已有的轮子。

**决策转向：**  
寻找成熟的管理系统底座。

### 页5：若依作为底座

**讲稿：**

这不是简单的"套个壳"，而是AI辅助对比后的决策。

**AI列出的方案：**
1. 自研完整后台
2. 升级Spring Boot 3
3. 使用若依3.6.8（Boot 2 + Java 8）

**人的约束：**
- 一人维护
- Java 8环境（公司基础设施）
- 必须Win+Mac
- 30303端口不可改（厂商限制）

**决策理由：**
- 权限菜单现成，节省token
- 微服务架构已搭好
- AI可以聚焦业务逻辑

**核心模块（强调不是套壳）：**
- **yianlian模块** — 这是AI辅助实现的核心业务
- **双服务层** — 本地库 + 远程同步
- **多线路ID映射** — `*YianlianMapping`表维护本地ID ↔ 远程ID

### 页6：Web端到客户端的演进

**讲稿：**

**第一版：Web端（MVP验证）**
- **Why：** 跨平台最快，验证统一登录和选线功能
- **验证目标：** 证明业务逻辑可行

**遇到安全问题：**
- HTTP明文传输
- 抓包可见密码
- 与零信任VPN的安全叙事矛盾

**第二版：桌面客户端**
- TLS 1.3加密
- Qt跨平台
- Win/Mac原生

**关键转折：**  
安全把第一解否决了。这不是失败，是架构演进。

**Web端下线：**  
用户端Web入口已下线，只保留管理端浏览器。

### 页9：客户端四选一（重点页，现场演示）

**讲稿：**

这是最有代表性的人机协作案例。

**Electron：**
- AI建议：出包快、前端熟、跨平台
- 人否决：安全面大、非原生

**Qt 6 + QML：**
- AI建议：原生、C++可迁移
- 人选择：Win/Mac一套代码

**WPF：**
- AI提示：只支持Windows
- 人否决：没有Mac

**ADR记录：**
- ADR-001：桌面端技术栈
- 四选一对比表
- 决策理由

**【现场演示建议】：打开ADR-001文件，展示四选一对比表（30秒）**

### 页10：协议与安全分级

**讲稿：**

**协议决策：**
- **AI倾向：** 复用HTTP网关、JSON格式、出活快
- **人否决：** 抓包风险
- **人决策：** TLS 1.3 + Protobuf :9443、证书Pin

**安全分级（S0/S1/S2）：**
- **S0只人验** — TLS配置、证书Pin、密钥、抓包验密文
- **S1人审逻辑** — 登录拦截、权限校验
- **S2脚本断言** — 只读查询、策略页

**关键：**  
S0永远只人验。栈配好了 ≠ 每个新功能自动过S0。

## 四、六阶段工作法（10分钟）

### 页11：节首页

**过渡：** 从实践中提炼出的方法，已沉淀SOP文档，在4个项目验证。

### 页12：六阶段全景

**讲稿：**

**① 拆解、② 共创（人主导）：**
- 模块清单、spec人批
- **硬门槛：未批spec不写码**

**③ 突破、④ 生成（按熟悉度分流）：**
- 陌生域（Vue/Qt）先Demo突破
- 熟悉域（Java）按规范生成
- 不另起炉灶

**⑤ 门禁、⑥ 回修（质量管控）：**
- gate → deploy → accept
- 质量门禁.md记录时间戳
- 回修≤2轮，超轮停下

**为什么是六阶段：**
- ①②防方向跑偏（人主导）
- ③④按熟悉度加速（分流）
- ⑤⑥质量可管控（门禁）

### 页13：人与AI配合

**讲稿：**

**人的职责：**
- 拆解边界
- 批准spec
- S0验收
- 架构决策

**AI的职责：**
- 列方案
- 生成代码
- 排错分析
- 即时导师
- **不承担责任**

**三个硬门槛：**
1. 未批spec不写码
2. S0只人验
3. 回修≤2轮，超轮停下

**可重复性：**
- 同一套命令
- 可搬迁到新项目
- 证据可核验

### 页14：质量门禁三命令

**讲稿：**

**gate：** 构建、单测、静态检查  
**deploy：** 三节点部署、服务健康、日志无异常  
**accept：** 业务验收、API断言、端到端流程

**--run参数：**
- 强制写入质量门禁.md
- 时间戳可追溯
- 证据可核验

**关键：** 没有--run记录，不能声称已过门禁。

## 七、问答预案（5分钟）

### Q1：「不就是套了若依吗？」

**答：**

若依是经过AI对比后的理性决策，不是套壳。

**核心业务（AI辅助实现）：**
- yianlian模块（双服务层）
- 多线路ID映射（`*YianlianMapping`表）
- 桌面客户端（TLS 1.3 + Qt跨平台）

### Q2：「Web端是不是失败了？」

**答：**

不是失败，是MVP验证。

- 第一版：快速验证业务逻辑可行
- 安全问题：HTTP明文、抓包可见密码
- 升级到客户端：安全驱动的架构演进

### Q3：「六阶段会不会太复杂？」

**答：**

恰恰相反，六阶段是为了让AI协作可控、可重复。

- ①②保证方向正确（未批spec不写码）
- ③④按熟悉度加速（陌生先突破）
- ⑤⑥质量可管控（回修≤2轮）

证据：08-15回修2轮通过，08-16当天三层打通。

### Q4：「能推广到我们团队吗？」

**答：**

可以，但需要适配。

**已提供：**
- SOP文档、工程实施手册
- 流水线搬迁文档
- Rule/Hook模板

**需要适配：**
- 构建命令（gate.py）
- 部署方式（deploy_impl.py）
- 验收逻辑（accept_impl.py）
- S0定义（什么算只人验）

### Q5：「客户端为什么不自动验收？」

**答：**

S0不能用页面文案代替抓包。

- TLS证书Pin需要人工确认
- 抓包验证密文需要人看工具
- 如果自动验收，会倒逼关验证码或识图回填，与安全红线冲突

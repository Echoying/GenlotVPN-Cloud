## 1. 文档目的与适用范围

### 1.1 文档目的

本 SOP 旨在解决以下问题：

1. **复杂项目协调成本高**：涉及后端、前端、客户端等多技术栈时，传统模式需 3～4 人分工协作，沟通与排期成本高。
2. **个人技术边界受限**：开发者通常只精通某一技术域，跨栈学习周期长，难以独立交付完整产品。
3. **AI 使用缺乏方法论**：多数开发者将 AI 当作「偶尔问几句」的辅助工具，未形成稳定、可复用的协作流程。
4. **质量与合规风险**：盲目采纳 AI 生成代码，可能引入安全漏洞、业务逻辑错误或不合规的数据使用。

本 SOP 提供一套经过实践验证的 **「开发 + AI」六阶段工作法**，帮助开发者在 AI 辅助下：

- **打破前端、后端、客户端的传统分工边界**
- **独立完成复杂全栈项目交付**
- **在提效的同时保障质量与合规**
- **沉淀可推广、可传授的团队工作范式**

### 1.2 适用范围

**适用项目类型：**

- 全栈管理系统（后端 + Web 管理端 + 用户端）
- 多端应用（Web + 桌面客户端 / 移动端）
- 多实例对接类平台（本地管理 + 远程多系统同步）
- 技术栈跨度大、模块多、协调成本高的复杂项目

**适用人员：**

- 后端开发者希望借助 AI 扩展至全栈交付
- 小团队（2～3 人）希望用 AI 提升人均产出
- 技术负责人希望建立团队 AI 协作规范

**不适用场景：**

- 极简单文件脚本、一次性数据处理
- 对安全合规要求极高且不允许 AI 参与的核心模块（如密钥管理核心逻辑）
- 无人工审核能力的全自动 AI 生成流程

### 1.3 验证案例

| 项目 | GenlotVPN 统一管理平台 |
|------|------------------------|
| 业务目标 | 替代公司老旧 VPN，实现总部/各省/海外零信任 VPN 统一登录，补齐精细化授权与使用审计 |
| 技术范围 | Java 微服务后端 + Vue 双端 Web + Qt 跨平台桌面客户端（Windows/macOS） |
| 开发者背景 | 后端开发工程师，无 Vue/Qt 实战经验 |
| 协作模式 | 1 人 + AI |
| 交付周期 | 约 2 个月（传统模式预估 3～4 人、6～9 个月） |

## 2. 术语定义

| 术语 | 定义 |
|------|------|
| **开发 + AI** | 开发者主导决策与质量，AI 辅助学习、生成、排错的协作模式 |
| **分域突破** | 在陌生技术领域，借助 AI 作为「即时导师」快速进入实战的方法 |
| **规范约束生成** | 用项目既有规范约束 AI 输出，使生成代码可融入现有工程 |
| **人工质量门禁** | 对 AI 生成内容进行的强制性人工审核环节，不可跳过 |
| **AI 即时导师** | 将 AI 作为 24 小时在线的技术顾问，边做边学边交付 |
| **复杂项目** | 涉及 2 个以上技术栈、3 个以上可独立验收模块的软件项目 |

## 3. 核心理念与原则

### 3.1 核心理念

> **人主导方向与质量，AI 加速学习、生成与排错。**

AI 不是替代开发者，而是 **能力放大器**：让一个人具备原本需要一个小组的能力结构。

### 3.2 六项核心原则

| 编号 | 原则 | 说明 | 违反后果 |
|------|------|------|----------|
| P1 | **人主导决策** | 拆什么、怎么拆、对不对——由人决定 | 项目方向失控 |
| P2 | **AI 加速执行** | 怎么写、怎么查、怎么学——交给 AI | 效率无法提升 |
| P3 | **规范约束输出** | 用项目规范约束 AI，避免代码无法融入工程 | 生成代码不可用 |
| P4 | **关键节点人工审核** | 权限、安全、业务逻辑必须人工把关 | 安全与质量风险 |
| P5 | **边做边学** | 陌生领域不先系统自学，而是 AI 即时导师 + 实战 | 学习周期过长 |
| P6 | **小步快跑** | 每次让 AI 生成一个模块，立即构建验证 | 错误累积、难以排查 |

### 3.3 人与 AI 的职责边界

```
┌────────────────────────────────────────────────────────┐
│  人（开发者）负责                                        │
│  · 业务目标与需求拆解                                    │
│  · 架构与技术选型决策                                    │
│  · 代码质量与安全审核                                    │
│  · 最终交付与责任承担                                    │
├────────────────────────────────────────────────────────┤
│  AI 负责                                                 │
│  · 架构方案建议与对比                                    │
│  · 代码初稿生成                                          │
│  · 新技术概念教学                                        │
│  · 报错分析与排查建议                                    │
│  · 不承担责任                                            │
└────────────────────────────────────────────────────────┘
```

```
┌─────────────────────────────────────────────────────────┐

                     ↓
┌─────────────────────────────────────────────────────────┐
│  阶段二：AI 共创设计                                     │

└────────────────────┬────────────────────────────────────┘
                     ↓
        ┌────────────┴────────────┐

┌───────────────┐           ┌───────────────┐
│ 阶段三：分域突破 │           │ 阶段四：规范生成 │
│ （陌生技术域）  │           │ （熟悉技术域）  │
└───────┬───────┘           └───────┬───────┘
        └────────────┬────────────┘
                     ↓
┌─────────────────────────────────────────────────────────┐
│  阶段五：人工质量门禁  ←── 不通过则返回阶段三/四修正      │

└────────────────────┬────────────────────────────────────┘
                     ↓
┌─────────────────────────────────────────────────────────┐

```

### 4.2 阶段关系说明

| 关系 | 说明 |
|------|------|
| 阶段一 → 二 | 项目初期串行完成，后续新模块可复用已有设计 |
| 阶段三 ↔ 四 | 按模块技术熟悉度选择：陌生领域走阶段三，熟悉领域可直接走阶段四 |
| 阶段五 | 每个模块生成后 **强制经过**，不可跳过 |
| 阶段六 | 模块联调阶段持续进行，可与阶段三～五并行 |
| 整体 | 阶段三～六按模块 **循环推进**，不同模块可并行 |

日常如何验收、如何定安全级、如何合入，见配套 **[工程实施手册](./开发+AI复杂项目六阶段工作法-工程实施手册.md)**，不在本 SOP 重复展开。

### 4.3 各阶段耗时参考（GenlotVPN 案例）

| 阶段 | 耗时占比 | 说明 |
|------|----------|------|
| 阶段一：人工拆解 | 约 5% | 1～2 天 |
| 阶段二：AI 共创设计 | 约 10% | 2～3 天 |
| 阶段三：分域突破 | 约 25% | Vue/Qt 零基础，边学边做 |
| 阶段四：规范约束生成 | 约 30% | 后端熟悉领域，AI 加速生成 |
| 阶段五：人工质量门禁 | 贯穿全程 | 每个模块必审 |
| 阶段六：AI 辅助迭代 | 约 30% | 联调排错占后期主要时间 |

## 5. 阶段一：人工拆解

### 5.1 阶段目标

将复杂系统拆分为 **可独立推进、可独立验证、可并行** 的模块，明确技术栈、优先级与依赖关系。

### 5.2 前置条件

- [ ] 业务需求或痛点清单已明确
- [ ] 项目技术约束已知（框架、部署环境、规范）
- [ ] 本人能力边界已评估（会什么、不会什么）

### 5.3 操作步骤

#### 步骤 1：梳理业务目标

列出项目要解决的 **核心问题** 和 **必须交付的能力**，不超过 5 条。

**GenlotVPN 示例：**

1. 同一账号统一登录总部/各省/海外零信任 VPN
2. 部门/角色/用户三级精细化授权
3. 全链路登录审计与看板统计
4. Windows/macOS 跨平台桌面客户端
5. 多线路统一管理与远程同步

#### 步骤 2：按技术域拆分模块

将系统按技术域划分为独立模块，每个模块应满足：

- 有明确的 **输入/输出**
- 可 **独立构建和验证**
- 有清晰的 **验收标准**

**模块拆分模板：**

| 模块编号 | 模块名称 | 技术栈 | 熟悉度 | 优先级 | 依赖模块 | 验收标准 |
|----------|----------|--------|--------|--------|----------|----------|
| M01 | | | 熟悉/一般/陌生 | P0/P1/P2 | | |
| M02 | | | | | | |

**GenlotVPN 模块清单：**

| 编号 | 模块名称 | 技术栈 | 熟悉度 | 优先级 | 依赖 | 验收标准 |
|------|----------|--------|--------|--------|------|----------|
| M01 | 后端微服务框架 | Java/Spring Cloud | 熟悉 | P0 | 无 | 服务启动、网关路由通 |
| M02 | 易安联多线路对接 | Java/HTTP | 一般 | P0 | M01 | 单线路增删改查同步成功 |
| M03 | 三级授权管理 | Java + Vue | 一般 | P0 | M01,M02 | 部门/角色/用户授权可配置 |
| M04 | 登录审计 | Java + Vue | 一般 | P0 | M01 | 登录日志可记录、查询、导出 |
| M05 | 管理端 Web | Vue/Element UI | 陌生 | P0 | M01～M04 | 全部管理页面可用 |
| M06 | VPN 用户端 Web（已下线） | — | — | — | — | 已由桌面客户端（M07）替代 |
| M07 | 桌面客户端 | Qt/C++/QML | 陌生 | P0 | M01 | Win/Mac 可构建、登录、连接 |
| M08 | 部署与工程化 | Docker/脚本 | 一般 | P1 | M01～M07 | 一键构建部署可用 |

#### 步骤 3：定义接口契约

明确模块间的 **API 接口、数据格式、调用方向**，避免后期联调时大规模返工。

**要点：**

- 先定义 **核心主链路** 的接口（如登录、选线、授权查询）
- 接口命名、响应格式与项目既有规范保持一致
- 可让 AI 辅助审查接口完整性，但 **契约由人确认**

#### 步骤 4：排优先级与里程碑

按 **主链路优先** 原则排期：

1. **第一波（P0）**：打通核心主链路，可演示端到端流程
2. **第二波（P1）**：完善管理功能、边缘场景
3. **第三波（P2）**：优化、监控、文档

**里程碑示例（2 个月周期）：**

| 周次 | 里程碑 | 交付物 |
|------|--------|--------|
| 第 1 周 | 架构确定 + 后端框架 | 服务启动、数据库初始化 |
| 第 2～3 周 | 核心业务后端 | 用户/授权/审计/多线路 API |
| 第 4～5 周 | 管理端 Web | 全部管理页面联调通过 |
| 第 5～6 周 | 桌面客户端 | Win/Mac 可登录连接 |
| 第 7～8 周 | 联调优化 + 上线准备 | 端到端流程通过、部署文档 |

### 5.4 输出物清单

- [ ] 《模块拆分清单》（含技术栈、熟悉度、优先级、依赖、验收标准）
- [ ] 《接口契约草案》
- [ ] 《里程碑计划》

### 5.5 质量检查

- [ ] 每个模块可独立验证
- [ ] 主链路模块已标注 P0
- [ ] 陌生技术栈模块已识别（后续走阶段三分域突破）
- [ ] 里程碑时间合理，首周可演示

### 5.6 常见错误

| 错误 | 后果 | 正确做法 |
|------|------|----------|
| 拆得过粗，整个前端当一个模块 | 无法分步验证 | 按功能页面或领域再拆 |
| 忽略依赖关系 | 后期联调阻塞 | 先画依赖图再排期 |
| 陌生模块未标注 | 低估工期 | 诚实标注熟悉度 |

## 6. 阶段二：AI 共创设计

### 6.1 阶段目标

借助 AI 补全架构盲区，完成 **可落地的技术方案**；所有关键决策由人做出并记录理由。

### 6.2 前置条件

- [ ] 阶段一《模块拆分清单》已完成
- [ ] 项目技术约束已整理（框架版本、目录结构、命名规范）

### 6.3 操作步骤

#### 步骤 1：向 AI 提供充分上下文

**必须提供的信息：**

```
- 项目背景与业务目标（3～5 条）
- 技术栈约束（框架、语言、版本）
- 项目目录结构（可粘贴关键目录树）
- 现有规范（命名、分层、接口格式）
- 本人能力边界（擅长什么、不擅长什么）
```

#### 步骤 2：要求 AI 给出多方案对比

**不要只问「怎么做」，而要问「有几种做法，各有什么优缺点」。**

示例 Prompt：

```
我要做一个 [项目描述]。
技术约束：[框架/语言/版本]
现有目录结构：[粘贴]
请给出 2～3 种架构方案，对比：
1. 模块划分
2. 技术选型
3. 优缺点
4. 实施风险
5. 哪个最适合 [我的背景/约束]
```

#### 步骤 3：多轮追问深化

对 AI 推荐的方案，必须追问：

- 边界情况如何处理？
- 与现有系统/框架如何集成？
- 有哪些已知坑或风险？
- 数据模型如何设计？
- 核心流程是什么？

#### 步骤 4：人工决策并记录

**AI 给建议，人做决策。** 记录：

- 选择了哪个方案
- 为什么选这个（而非其他）
- 已知风险与应对

#### 步骤 5：输出设计文档

整理为可执行的设计文档，供后续阶段引用。

### 6.4 GenlotVPN 设计决策示例

| 设计问题 | AI 建议 | 人工决策 | 决策理由 |
|----------|---------|----------|----------|
| 多线路如何管理 | 方案 A：配置中心 / 方案 B：数据库+映射表 | 方案 B | 需持久化映射关系，支持按线路独立同步 |
| 前端技术 | React / Vue | Vue 2 | 项目已采用 Vue，保持一致 |
| 客户端技术 | Electron / Qt | Qt 6 | 性能更好，适合 VPN 本地通信场景 |
| 认证方式 | 统一网关 / 独立认证服务 | 独立 VPN 认证网关 | 与系统管理端认证隔离 |
| 授权模型 | 扁平 / 三级 | 部门+角色+用户三级 | 满足最小权限与灵活配置 |

### 6.5 输出物清单

- [ ] 《架构设计说明》（含技术选型与决策理由）
- [ ] 《核心数据模型》（ER 图或表结构）
- [ ] 《关键业务流程图》（登录、授权、同步等）
- [ ] 《AI 对话记录节选》（脱敏，作知识沉淀）

### 6.6 质量检查

- [ ] 每个关键决策有明确理由

## 7. 阶段三：分域突破

### 7.1 阶段目标

在 **零基础或薄弱的陌生技术领域**，借助 AI 作为「即时导师」，快速产出可运行的代码，**边做边学，学习与交付同步进行**。

### 7.2 适用场景

| 开发者背景 | 陌生领域 | 典型场景 |
|------------|----------|----------|
| 后端 | 前端 Vue/React | 管理后台页面开发 |
| 后端 | 客户端 Qt/Electron | 桌面应用开发 |
| 前端 | 后端 Java/Go | 服务端 API 开发 |
| 任意 | 陌生协议/工具 | Protobuf、CMake、Docker 等 |

### 7.3 操作步骤

#### 步骤 1：明确本模块验收标准

用 **可验证** 的语言描述「做完」的标准：

> ❌ 「完成前端开发」
> ✅ 「VPN 用户管理页可列表查询、新增、编辑、删除，与后端 API 联调通过」

#### 步骤 2：让 AI 解读项目现有规范

```
我是 [后端] 开发者，没有 [Vue] 经验。
本项目使用 [Spring Cloud + Vue 2 + Element UI]。
目录结构如下：[粘贴管理端前端 src 关键目录]
请说明：
1. 新增一个管理页面的标准步骤
2. 需要创建哪些文件
3. 各文件的职责
4. 一个最简单的列表页示例
```

#### 步骤 3：跑通第一个最小示例

**关键：先跑通一个最简单的 Demo，再扩展。**

- 让 AI 生成最小可运行示例
- 本地构建运行，确认能工作
- 理解示例的基本结构

#### 步骤 4：在示例基础上逐步扩展

每次只加一个功能点：

```
第 1 步：静态列表页（假数据）
第 2 步：对接后端 API
第 3 步：加分页
第 4 步：加搜索
第 5 步：加新增/编辑弹窗
第 6 步：加删除与权限控制
```

每步完成后 **立即构建验证**，不要累积多步再测。

#### 步骤 5：遇错即问

将 **完整报错信息 + 相关代码片段 + 已尝试的方法** 交给 AI 分析（参见阶段六排错模板）。

## 8. 阶段四：规范约束生成

### 8.1 阶段目标

在 **已有规范或参照模块** 的技术域，约束 AI 按项目规范生成代码，使输出 **可直接融入工程**。

### 8.2 与阶段三的区别

| | 阶段三：分域突破 | 阶段四：规范约束生成 |
|--|------------------|----------------------|
| 适用 | 陌生技术域 | 熟悉或有参照的技术域 |
| 重点 | 学习 + 跑通 Demo | 按规范批量生成 |
| AI 角色 | 即时导师 | 代码生成器 |
| 人的工作 | 理解概念、验证能跑 | 审核规范符合度 |

### 8.3 操作步骤

#### 步骤 1：选定参照模块

在项目中找一个 **结构最接近** 的已有模块作为参照。

**GenlotVPN 参照关系：**

| 目标模块 | 参照模块 |
|----------|----------|
| VPN 用户管理页 | system/user/index.vue |
| VPN 用户 Controller | VpnUserController ← SysUserController 模式 |
| 授权 Service | YalUserAuthService ← 项目既有权限模式 |
| 登录日志 | VpnLogininfor ← SysLogininfor 模式 |

#### 步骤 2：编写规范约束 Prompt

参见 [附录 B：Prompt 模板库](#附录-bprompt-模板库)。

**必须包含的约束：**

1. 框架与版本
2. 参照文件路径
3. 目标功能描述
4. 命名与结构要求
5. 只输出需要新增/修改的文件

#### 步骤 3：生成并检查

- AI 生成代码后，**先检查结构和命名**，再检查业务逻辑
- 不符合规范 → 补充约束 → 让 AI 修正
- 符合规范 → 进入阶段五质量门禁

#### 步骤 4：批量生成同类模块

第一个模块审核通过后，后续同类模块生成速度会显著加快（AI 有了好的参照）。

### 8.4 提高 AI 输出可用率的技巧

| 技巧 | 说明 |
|------|------|
| **给参照代码** | 粘贴或指定参照文件，而非纯文字描述 |
| **约束输出范围** | 「只生成 xxx 文件，不要改其他文件」 |
| **一次一个模块** | 不要一次生成整个系统 |
| **明确文件路径** | 「文件放在 src/views/vpn/user/index.vue」 |
| **迭代修正** | 第一版不满意，指出具体问题让 AI 改 |

## 9. 阶段五：人工质量门禁

### 9.1 阶段目标

对 AI 生成内容执行 **强制性人工审核**，确保业务正确、安全合规、代码规范。**本阶段不可跳过。**

### 9.2 门禁原则

> **AI 可以加速生成，但不能替代责任。**
> 凡 AI 参与生成的代码，合入工程前必须经过本阶段审核。

### 9.3 审核流程

```
AI 生成代码
    ↓
开发者按 Checklist 逐项审核
    ↓
  ┌─ 通过 → 合入工程 / 进入联调
  │
  └─ 不通过 → 标注问题
              ↓
         AI/人工修正
              ↓
         重新审核（回到 Checklist）
```

### 9.4 审核 Checklist

#### 9.4.1 业务逻辑

- [ ] 核心流程符合需求文档/设计文档
- [ ] 边界情况已处理（空值、重复提交、并发）
- [ ] 与关联模块的数据流一致
- [ ] 异常场景有合理提示

#### 9.4.2 权限与安全

- [ ] 接口有权限注解（如 `@RequiresPermissions`）
- [ ] 无 SQL 注入风险（参数化查询）
- [ ] 无 XSS 风险（前端输入转义）
- [ ] 敏感数据加密存储、脱敏展示
- [ ] 认证/授权逻辑正确，无越权漏洞
- [ ] 日志中不打印密码、密钥等敏感信息

#### 9.4.3 代码质量

- [ ] 符合项目命名规范（类名、方法名、变量名）
- [ ] 符合项目分层规范（Controller → Service → Mapper）
- [ ] 无明显的死代码或冗余逻辑
- [ ] 异常处理合理，不吞异常
- [ ] 无硬编码的配置项（应走配置中心或环境变量）

#### 9.4.4 AI 特有风险

- [ ] 未引入不存在的 API、类、依赖
- [ ] 未「看起来对」但逻辑错误的代码（重点看条件判断、循环、事务）
- [ ] 未过度设计（引入项目不需要的复杂模式）
- [ ] 未与项目风格脱节（如用了项目未使用的库）

### 9.5 重点审核模块

以下模块建议 **人工主导设计，AI 仅辅助实现**：

| 模块类型 | 原因 |
|----------|------|
| 认证与登录 | 安全核心，错误影响全局 |
| 权限与授权 | 越权风险高 |
| 审计与日志 | 合规要求，数据不可丢 |
| 加密与通信 | 安全核心 |
| 密码与密钥处理 | 泄露风险极高 |

### 9.6 审核记录

对关键模块，建议保留简要审核记录：

| 模块 | 审核日期 | 审核人 | 结果 | 发现问题 | 处理 |
|------|----------|--------|------|----------|------|
| VpnUserController | | | 通过/不通过 | | |

- [ ] 审核通过的代码模块
- [ ] 《AI 质量门禁 Checklist》（本文档 9.4 节）
- [ ] 关键模块审核记录

## 10. 阶段六：AI 辅助迭代

### 10.1 阶段目标

在联调、测试、排错阶段，借助 AI **加速问题定位**，由人做最终判断与修复。

### 10.2 适用场景

- 编译/构建失败
- 前后端接口不一致（字段、类型、状态码）
- 运行时异常与堆栈报错
- 跨平台兼容问题（Windows vs macOS）
- 性能问题与偶发 Bug

### 10.3 操作步骤

#### 步骤 1：复现并收集信息

在向 AI 提问前，确保收集：

- [ ] 问题的 **准确现象**（期望 vs 实际）
- [ ] **完整报错信息**或堆栈
- [ ] **相关代码片段**（不要整个文件，只要相关部分）
- [ ] **已尝试的方法**（避免 AI 重复建议）
- [ ] **环境信息**（OS、框架版本、构建类型）

#### 步骤 2：使用排错 Prompt 模板

参见 [附录 B.4：排错分析 Prompt](#b4-排错分析-prompt)。

#### 步骤 3：评估 AI 建议

- AI 的分析是否合理？
- 建议的修复是否引入新问题？
- 是否有更简单的修复方式？

**不盲目执行 AI 建议，先理解原因再修复。**

#### 步骤 4：修复并验证

- 执行修复
- 验证原问题已解决
- 验证未引入新问题
- 记录案例

## 14. 常见问题 FAQ

**Q1：我没有前端/客户端经验，能用这套方法吗？**

可以。阶段三「分域突破」专为此设计。关键是把 AI 当即时导师，边做边学，不要试图先系统学完再动手。GenlotVPN 案例证明后端开发者可在约 2 周内上手 Vue 页面开发。

**Q2：AI 生成的代码能直接用吗？**

不能。必须经过阶段五质量门禁。实践表明 AI 生成代码约 70%～80% 可用，剩余需人工修正，安全相关模块需重点审核。

**Q3：六阶段必须严格按顺序吗？**

阶段一、二在项目初期串行完成。阶段三～六按模块循环，可并行推进不同模块。阶段五对每个模块都是强制环节。

**Q4：一个人能做，团队怎么用？**

- 共用阶段二的设计文档和接口契约
- 共用阶段四的 Prompt 模板库
- 共用阶段五的质量门禁 Checklist
- 各成员按模块分工，各自走阶段三～六

**Q5：如何向团队推广？**

1. 用真实项目案例（如 GenlotVPN）演示效果
2. 组内分享六阶段工作法（约 30～45 分钟）
3. 将本 SOP 与 Prompt 模板库入库
4. 鼓励同事在自己的项目中试用并反馈

**Q6：哪些环节 AI 帮不上忙？**

- 业务需求判断与优先级决策
- 安全架构的最终拍板
- 与业务方/主管的沟通协调
- 生产环境的运维与应急

**Q7：2 个月交付靠谱吗？有什么前提？**

前提条件：开发者熟悉核心业务领域（如 GenlotVPN 中开发者熟悉后端）；AI 工具可用且网络畅通；项目有清晰的需求边界，范围不膨胀；质量门禁不省略但审核聚焦关键点。
